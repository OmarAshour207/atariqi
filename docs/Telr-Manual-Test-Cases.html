1. Telr Payment Gateway Overview

Atariqi uses Telr hosted payment pages for driver subscription payments and dues payments. Configuration is in config/telr.php and .env. Payment events are logged to storage/logs/payment/.

FlowEntry PointCompletion
Subscribe to PackagePOST api/driver/subscribeTelr webhook → activate subscription
Upgrade PackagePOST api/driver/subscribe (with existing package)Telr webhook → upgrade subscription
Pay DuesPOST api/driver/dues/payTelr webhook → record FinancialDue
Cancel SubscriptionPOST api/driver/cancelDirect (no Telr — moves to free plan)
Note: Return URLs after Telr checkout: authorised → /payment/telr/success, declined → /payment/telr/declined. Cancelled URL is configured as /payment/telr/cancel but this route may not be registered — verify in routes/web.php.

2. Driver Subscription Payment

Endpoint: POST api/driver/subscribe

Route name: Create Subscription Payment Session

Note: Requires auth:sanctum + is_driver middleware.

Test Case 1: New Subscription — Monthly

Objective: First-time subscription

Steps:

  1. Login as driver with no active UserPackage
  2. POST package_id and type=monthly for active paid package
  3. Check response

Expected Result:

Returns 200 JSON: success=true, payment_url (Telr hosted page), order_ref. Order created with status=PENDING, type=subscription, interval=monthly. payment_gateway_id saved after Telr session created.

Test Case 2: New Subscription — Yearly

Objective: Annual plan

Steps:

  1. Login as driver without package
  2. POST package_id and type=yearly
  3. Check response

Expected Result:

Order amount = package price_annual. payment_url returned. Order type=subscription, interval=yearly.

Test Case 3: Upgrade Existing Package

Objective: Driver has active package

Steps:

  1. Login as driver with active paid package
  2. POST different package_id or different interval
  3. Check response

Expected Result:

Order type=upgrade (not subscription). payment_url returned. Amount based on selected interval price.

Test Case 4: Already Subscribed — Same Package

Objective: Duplicate subscription

Steps:

  1. Login as driver already on same package_id and interval
  2. POST same package_id and type

Expected Result:

422 error: "You are already subscribed to this package." No new order created.

Test Case 5: Inactive Package

Objective: SOON status package

Steps:

  1. POST package_id for package with status=SOON
  2. Submit

Expected Result:

422 error: "This package is not active." No order created.

Test Case 6: Validation Errors

Objective: Missing/invalid fields

Steps:

  1. POST without package_id
  2. POST with invalid type (not monthly/yearly)
  3. POST with non-existent package_id

Expected Result:

422 Validation Error with field-specific messages.

Test Case 7: Telr Session Creation Failure

Objective: Telr API error

Steps:

  1. Configure invalid TELR_STORE_ID or TELR_AUTH_KEY
  2. POST valid subscribe request

Expected Result:

400 response: success=false with Telr error message. Order remains PENDING without payment_gateway_id.

Endpoint: POST api/driver/cancel

Route name: Cancel Subscription (No Telr)

Test Case 1: Successful Cancellation

Objective: Move to free plan

Steps:

  1. Login as driver with active paid subscription
  2. Ensure free package exists in database
  3. POST api/driver/cancel

Expected Result:

200 OK: "You have successfully canceled the subscription." Old package moved to UserPackageHistory with status=CANCELLED, canceled_date=today. New free package assigned (yearly, active, end_date=today+1 year).

Test Case 2: No Active Subscription

Objective: Nothing to cancel

Steps:

  1. Login as driver with no UserPackage record
  2. POST cancel

Expected Result:

422: "You do not have an active subscription." No DB changes.

Test Case 3: Already Cancelled

Objective: Duplicate cancel attempt

Steps:

  1. Login as driver whose package status is already CANCELLED
  2. POST cancel

Expected Result:

422: "You have already canceled your subscription." (if applicable) OR "You do not have an active subscription." depending on state.

Test Case 4: Free Package Not Found

Objective: Missing free plan

Steps:

  1. Remove all free packages from DB
  2. Login as driver with active paid subscription
  3. POST cancel

Expected Result:

500 error with exception about null free package. Transaction rolled back. Original package remains.

Test Case 5: Transaction Rollback

Objective: DB failure during cancel

Steps:

  1. Simulate DB error during cancellation
  2. POST cancel

Expected Result:

500 error. Complete rollback. Original subscription intact.

Test Case 6: Sequential Cancel Attempts

Objective: Idempotency check

Steps:

  1. Cancel successfully first time
  2. Immediately POST cancel again

Expected Result:

First: 200 success. Second: 422 no active subscription. Driver ends on free plan only.

Test Case 7: Unauthenticated

Objective: Auth required

Steps:

  1. POST cancel without Bearer token

Expected Result:

401 Unauthorized.

4. Telr Webhook

Endpoint: POST api/webhook/telr

Route name: telr.webhook — Payment Notification Handler

Note: Public endpoint — no authentication. Telr sends POST with tran_status, tran_cartid, and other fields.

Test Case 1: Authorized — Subscription Payment

Objective: tran_status=A, type=subscription

Steps:

  1. Create pending subscription order via api/driver/subscribe
  2. Simulate Telr webhook POST with tran_status=A and tran_cartid=order.id
  3. Check DB

Expected Result:

Order status updated to COMPLETED. UserPackage created (active, correct dates based on interval). UserPackageHistory record created. Response: "You have successfully subscribed to the package." Logged to storage/logs/payment/.

Test Case 2: Authorized — Upgrade Payment

Objective: tran_status=A, type=upgrade

Steps:

  1. Create pending upgrade order
  2. Send webhook with tran_status=A

Expected Result:

Old UserPackage moved to history with canceled_date. Old package deleted. New UserPackage created. Response: "You have successfully upgraded the package."

Test Case 3: Authorized — Dues Payment

Objective: tran_status=A, type=pay_due

Steps:

  1. Create pending dues order via dues/pay
  2. Send webhook with tran_status=A

Expected Result:

Order status=COMPLETED. FinancialDue record created with amount and date. Response: "Dues payment completed successfully."

Test Case 4: Failed/Declined Payment

Objective: tran_status != A

Steps:

  1. Create pending order
  2. Send webhook with tran_status=D (declined) or other non-A status

Expected Result:

Order status updated to FAILED. Logged as payment failed. Response: {"status":"success"} (acknowledges webhook).

Test Case 5: Unknown Order ID

Objective: Order not found

Steps:

  1. Send webhook with tran_cartid that does not match pending order
  2. Submit

Expected Result:

Response: {"status":"ignored"}. No DB changes.

Test Case 6: Already Processed Order

Objective: Non-pending order

Steps:

  1. Send webhook for order already COMPLETED
  2. Submit again

Expected Result:

Order not found (status != PENDING). Response: {"status":"ignored"} or order marked FAILED incorrectly — verify behavior.

Test Case 7: Webhook DB Transaction Rollback

Objective: Subscription processing failure

Steps:

  1. Simulate DB error during subscribe() webhook handler
  2. Send authorized webhook

Expected Result:

500 error returned. Transaction rolled back. Order remains PENDING. No UserPackage created. Error logged to payment channel.
